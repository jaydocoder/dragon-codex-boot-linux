# ScreenFrames 标定说明

本文记录 `screenFrames` 是怎么来的、为什么**不能**自动标定，以及 `src/calibrate.py`
到底能做什么。结论先写在前面：

> **`screenFrames` 以上游人工量取的值为准。本项目不提供「一键自动标定」，
> `src/calibrate.py` 是校验与微调工具，不是求解器。**

## 1. screenFrames 是什么

`geometry.dest()` 需要知道：在视频的某个时间点，画面里那块「屏幕矩形」处于什么
位置、有多大。这个信息就是 `screenFrames`：一组 `(Time, X, Y, Width, Height)`，
坐标是相对整幅画面的归一化值（0~1）。

动画末尾屏幕矩形逐步放大到铺满整幅画面；配合 `ease(fade)` 插值，真实的应用窗口
就从「屏幕矩形的位置」平滑长到「整个播放窗口」。

本项目使用的默认值（1920×1080 归一化，来自上游 `launcher.json`）：

| Time  | X     | Y     | Width | Height |
|-------|-------|-------|-------|--------|
| 12.65 | 0.123 | 0.094 | 0.736 | 0.725  |
| 13.00 | 0.074 | 0.061 | 0.845 | 0.825  |
| 13.50 | 0.000 | 0.000 | 1.000 | 1.000  |
| 13.65 | 0.000 | 0.000 | 1.000 | 1.000  |

换算成 1920×1080 像素：`(236,102,1413,783)`、`(142,66,1622,891)`、
`(0,0,1920,1080)`。`tests/test_geometry.py` 里有独立的黄金值复算，保证移植后的
`geometry` 与上游数值一致。

## 2. 为什么不能自动标定

最初的设想是「像素差分求出屏幕矩形」：屏幕区域内是应用画面，区域外是背景，只要
拿到两者的差异像素外接矩形就能定位边界。对 `media/startup.mp4` 实测后，这条路
在每一个环节上都断了。

### 2.1 边界本身不存在可检测的边缘

沿真值边界取 ±6 像素的灰度剖面：

```
t=12.65  y=500, x=236  →  [238,237,235,235,234,234,234|234,234,234,236,234,232]  跳变 6
t=12.65  y=500, x=1649 →  [235,235,235,236,236,236|236,237,237,238,238,240,239]  跳变 5
t=13.30  y=500, x=236  →  全 238                                              跳变 0
```

垂直方向的边界略有信号（跳变 28~35），水平方向几乎没有。H.264 在平坦亮色区域
的高频量化会把这种低对比度的边缘直接抹平——**信息在编码阶段就丢了，不是解码
或采集的问题**（用 `ffmpeg` 直接抽帧与用 mpv `seek` + `screenshot-raw` 结果一致）。

### 2.2 背景不是暗色星空，而是和屏幕同样明亮的渐变

实测各时间点整帧灰度均值：`11.0s → 228.9`、`12.65s → 224.1`、`13.0s → 233.8`、
`13.5s → 243.3`。屏幕内外亮度都在 230~250 区间，**亮度阈值分割无从下手**。

局部方差也不行：13.0s 处真值内部的块级标准差中位数是 16.7，而真值外部下带的
块级标准差中位数是 14.56，两者重叠到无法用一个阈值分开。

### 2.3 背景自身在变化，不能当差分基准

以「已铺满」的 13.9s 帧做基准逐点差分，全部采样点（含 10.0s、11.0s）的外接
矩形都撑满整幅 1920×1080，差异比例 0.63~0.67。背景渐变在缓慢漂移，**任何基于
远端基准的差分都会退化成全屏**。

### 2.4 唯一有效的信号：同一时间点的连拍帧差分

在同一个时间点连续抓 3 帧（间隔约 40ms），静止的背景完全一致，只有屏幕区域
内部的画面在动，于是差异矩形恰好落在屏幕区域上。实测这条判据在 12.4~12.8s
可用，误差 3~8 像素。

**但它不覆盖过渡末段**：13.0s 之后画面已接近纯色平坦，连拍帧完全相同，差分
返回 `None`。而 13.0s 正是最关键的关键帧之一。

## 3. `src/calibrate.py` 的实际能力

基于上面的结论，`calibrate()` 被设计成**种子模式**：

```python
result = calibrate(
    samples,              # sample_frames() 的返回值
    width, height,        # 帧尺寸
    seeds=existing_frames # 上游已量好的关键帧，作为初值
)
result.frames   # 最终关键帧
result.report   # 逐点结论：refined / seed / diff / none
result.trusted  # 是否每个采样点都有可信结论
```

逐点行为：

| 连拍差分 | 有种子 | 结论 | 采用值 |
|----------|--------|------|--------|
| 有信号，与种子偏差 ≤ 2% | 是 | `refined` | 差分值（微调） |
| 有信号，与种子偏差 > 2% | 是 | `seed` | 种子值（差分不可信） |
| 无信号（画面静止） | 是 | `seed` | 种子值 |
| 有信号 | 否 | `diff` | 差分值，**标注未校验** |
| 无信号 | 否 | `none` | 不产出关键帧 |

`snap_tolerance` 默认 `DEFAULT_SNAP_TOLERANCE = 0.02`，约合 1920×1080 上的
38×22 像素。

**没有 `seeds` 时工具不会替你猜边界**，只会如实报告哪些时间点有运动信号，
并让 `result.trusted` 为 `False`。

## 4. 适用边界

这套工具在以下情况有意义：

- 换了视频素材（比如更高对比度、边界清晰的新版动画），想复核上游给的值；
- 微调：上游值与实际素材差了几个像素，想量化偏差；
- 换分辨率重新量取时，用缩放后的旧值做种子。

以下情况**不要**指望它：

- 拿一段完全没有种子的新视频从零反推 `screenFrames`；
- 期望它在 `startup.mp4` 这类低对比度、背景同亮的素材上自动收敛。

需要真正从零量取时，正确的做法是用视频编辑器或 `ffmpeg` 抽帧后人工量取——
这比调参可靠得多，而且只需做一次。

## 5. 常见问题

**Q：`strict` 模式下为什么 `trusted=False`？**

A：说明有采样点既没有种子值、也没有运动信号，工具无从判断。用 `--seed-from`
指向已有的 `launcher.json` 即可。

**Q：为什么 `sample_frames` 用 `vo=null`？**

A：标定不需要真的把画面渲染到屏幕上。`vo=null` 只解码不输出，因此可以在无窗口、
甚至 headless 的会话里跑。

**Q：`row_stride()` 为什么不等于 `width * 3`？**

A：mpv `screenshot-raw` 返回的缓冲区按 4 字节对齐。宽度为奇数时每行会补 1~3
字节填充，按 `width * 3` 切行会把上一行的尾部误当成当前行开头。

**Q：为什么不直接用 `player.screenshot_raw`？**

A：python-mpv 的该包装依赖 Pillow，本项目刻意不引入额外图像库，因此直接调用
底层 `player.command("screenshot-raw", "video")` 自行处理 `bgr0 → RGB24`。
